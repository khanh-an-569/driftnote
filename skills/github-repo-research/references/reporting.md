# Repository research reports / Báo cáo nghiên cứu repo

Use the smallest report shape that answers the request. A useful comparison normally includes the repository name and direct GitHub URL, the problem it appears to solve, evidence-backed strengths, constraints or unverified fields, fit against the user's criteria, and a concise recommendation or next validation step.

Dùng cấu trúc ngắn nhất vẫn trả lời đủ yêu cầu. Một bản so sánh hữu ích thường gồm tên và URL repo, bài toán repo giải quyết, điểm mạnh có bằng chứng, giới hạn hoặc mục chưa xác minh, độ phù hợp với tiêu chí của người dùng và đề xuất ngắn.

## Evidence rules / Quy tắc bằng chứng

- Cite the repository URL beside claims about that repository. / Đặt URL repo cạnh nhận định về repo đó.
- Treat Tavily relevance scores as ranking hints, not quality scores. / Xem relevance score của Tavily là gợi ý xếp hạng, không phải điểm chất lượng.
- Search snippets may support a capability summary, but not volatile metadata such as stars, recent commits, releases, open issues, or maintenance status. / Snippet có thể hỗ trợ tóm tắt năng lực, nhưng không đủ cho metadata dễ đổi như stars, commit gần nhất, release, issue hoặc trạng thái bảo trì.
- Mark missing evidence explicitly instead of filling gaps from memory. / Ghi rõ phần thiếu bằng chứng thay vì điền bằng trí nhớ.
- When several queries surface the same repository, treat that as broader query coverage, not proof of superiority. / Repo xuất hiện ở nhiều truy vấn cho thấy độ phủ truy vấn rộng hơn, không chứng minh repo tốt hơn.

## Recommendation criteria / Tiêu chí đề xuất

Derive criteria from the user's request. If none are supplied, use a modest default set: functional fit, clarity of documented usage, integration cost, evidence of an active project, and licensing clarity. Verify each criterion or leave it unknown.

Suy ra tiêu chí từ yêu cầu của người dùng. Nếu chưa có, dùng bộ mặc định vừa phải: độ phù hợp chức năng, độ rõ của hướng dẫn sử dụng, chi phí tích hợp, bằng chứng dự án còn hoạt động và độ rõ về giấy phép. Xác minh từng tiêu chí hoặc để chưa xác minh.

For a long-form report, keep a brief method note with the exact queries, search date, filters (`github.com` only), and known limitations. End with concrete follow-up checks rather than presenting a weakly evidenced winner.

Với báo cáo dài, thêm ghi chú phương pháp gồm truy vấn chính xác, ngày tìm kiếm, bộ lọc (chỉ `github.com`) và giới hạn đã biết. Kết thúc bằng các bước xác minh cụ thể thay vì chọn một “người thắng” dựa trên bằng chứng yếu.
